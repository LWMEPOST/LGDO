## 1. 结论摘要

项目并不是“完全没有 Obsidian”，而是经历了两个不同阶段：原始实现只把 Markdown 写到 Vault，Obsidian 只是可打开的兼容出口；本轮实现才把它提升为可持续运行的文件系统工作流。当前链路已经具备稳定身份、双向观察、冲突留痕、删除过期恢复、GBrain 投影 outbox、引用校验和 Obsidian deep link，但仍然没有官方 Obsidian 插件或 Obsidian API 进程内集成。

因此，用户此前看到“Obsidian 没有实现”的根本原因是产品边界和文档表述不一致：代码有 Markdown 产物，却缺少 watcher、稳定 page identity、reconcile、删除竞态和冲突 UI 所需的完整闭环。README 也曾把 Obsidian 写成“兼容出口”，进一步造成了未实现的印象。

截至本次终审，代码闭环已经完成并具备合并条件。此前“仍像没有实现”主要来自三类边界混淆，而不是单一代码缺失：

1. 实现最初位于独立工作树，项目根目录当时仍停留在另一开发分支；本次交付已冻结变更、完成全量门禁，并按独立分支提交后合入 `main`，没有覆盖根工作区的其他未提交工作。
2. 已启动的 `8117` 是隔离验收实例，其 GBrain query/projection 是否启用取决于启动时配置。代码和 `.env.example` 已支持 query/projection 分离 token、managed source 和 allowed root；部署实例仍须显式配置并重启，不能用旧进程状态判断仓库是否实现。
3. 当前产品目标是共享 Vault 文件工作流，不是 Obsidian 原生插件。冲突、revision、citation 和重试仍由 LGDO Web 控制台/API 承担。

所以，本报告对代码能力的判断是“共享 Vault 闭环已实现并通过回归”；若验收口径要求 Obsidian 原生侧边栏、命令面板或插件市场安装包，则该部分仍属于下一阶段。

本轮复审的工程判断：

- revision/冲突模型已从“覆盖文件”改为 immutable revision + write intent + CAS + conflict review。
- GBrain 导入阻塞的核心原因是身份字段缺失、批量结果归因歧义和保护记录过早释放；已改为 `id == page_id`、批次快照、同状态多 job 归因、fail-closed protection 和原子 CAS。
- citation 契约已把来源、页路径、hash、权限过滤和 GBrain 映射统一到检索结果，生成模型不能绕过证据校验。
- Obsidian 工作流采用共享 Vault，不依赖插件：LGDO 写入托管 Markdown，watcher 接收 Obsidian 外部编辑，revision service 负责冲突和恢复。
- 认证默认已改为 fail-closed；上传 domain 在写盘前做 root containment；PostgreSQL 测试改为 UUID 数据库并证明 ownership；测试默认网络门禁拒绝固定运行端口和外网凭据。

## 3. 实际技术栈与职责边界

### 3.1 LLMWiki

LLMWiki 不是仓库外部的独立服务，而是项目内的知识编译层。`compile_wiki` 从已标准化的来源读取文本，创建或更新 `wiki_pages`、revision 和审阅记录，并通过 `WikiRevisionService` 维护生成候选、人类编辑、恢复和冲突状态。它输出的是可读 Markdown，而不是直接把文件当作唯一事实源。

### 3.2 GBrain

GBrain 是仓库内 `gbrain/` 的 TypeScript/Bun MCP 服务，默认使用 PGLite，也可以通过 HTTP MCP 常驻运行。Python 侧分成两条路径：

- `app/gbrain.py` 负责查询、熔断、候选归一化、超时和可选的整库导入。
- `app/gbrain_projection.py` 负责按 page/revision/projection epoch 把 Wiki 页面投影到 GBrain，并通过 projection outbox、批次快照和保护记录处理重试、删除与竞态。

GBrain 是派生图谱，不替代 `wiki_pages` 和 revision 表的权威状态。

### 3.3 DeepSeek

DeepSeek 只承担检索后的自然语言生成。`app/search.py` 先构造本地/GBrain 证据，`app/llm.py:generate_answer` 在配置了 `DEEPSEEK_API_KEY` 和模型时调用兼容 API；未配置或调用失败时，系统回退到本地抽取式回答。它不负责 revision、文件同步或图谱身份。

### 3.4 Obsidian

当前 Obsidian 集成是“共享 Vault + watcher + deep link”模式：

1. LGDO 将托管 Markdown 写入配置的 Vault。
2. Markdown frontmatter 同时保存 `id` 和 `lgdo_page_id`，两者都等于稳定的 `wiki_pages.page_id`。
3. Obsidian 的人工修改由文件 watcher 捕获，经过稳定性观察、路径/身份校验和 revision service 进入外部 revision。
4. 生成文件与人工文件发生分歧时，不覆盖人工内容，而是创建 review/conflict 记录并保留可恢复备份。
5. `/api/internal/wiki/pages/{path}/obsidian-link` 生成 `obsidian://open?...` deep link。

当前没有 `manifest.json`、Obsidian Plugin API 或插件进程。因此它是可靠的文件系统工作流，但不是“原生插件集成”；后续若要在 Obsidian 内显示冲突按钮、同步状态和引用面板，仍需单独开发插件。

## 4. 为什么此前会被认为 Obsidian 没有实现

### 4.1 只有产物，没有运行时闭环

早期链路能生成 `vault/wiki/*.md`，但没有长期运行的 watcher、启动前 reconcile、删除过期 scheduler 和失败重试。用户在 Obsidian 中编辑后，数据库 revision、RAG chunk 和 GBrain 映射不能可靠收敛。

### 4.2 身份契约不完整

仅有文件路径或 slug 不能承受 rename、restore、同名页面和重放。GBrain 需要通用 `id` 字段，而 Wiki 页面原先只稳定维护 `lgdo_page_id` 或路径，导致导入阶段无法把返回结果唯一归因回页面。

### 4.3 GBrain 批量结果存在归因歧义

同一 page 的 rename + upsert 可能在一个批次中产生多个 job；如果按 job 数量直接判定歧义，会把本应成功的结果全部失败。相反，不同 revision/epoch 混在一起又必须 fail-closed。现在按 `(page_id, revision_id, projection_epoch)` 分组，并按 `(created_at, id)` 确定最终 `last_job_id`。

### 4.4 删除保护与 restore 存在竞态

删除失败时必须保护原 slug/source path，其他 page 或 `page_id=NULL` 的保护不能被“自身删除成功”顺手清掉；请求前或请求中 restore 也不能把旧 delete 结果应用到新页面。原实现缺少这些边界，所以 GBrain 可能超时、重复导入或误删除。

### 4.5 文档把 Obsidian 降级成兼容出口

README 之前使用“Obsidian-compatible”表述，没有说明 watcher、frontmatter identity、reconcile 和 deep link，读者自然会把它理解为导出格式，而不是系统工作流。

## 5. 本轮已完成的关键修复

### 5.1 Revision 与冲突

- 生成、人类编辑、外部 watcher 事件都创建 immutable revision。
- write intent 记录预期 revision、文件 hash、写入 token 和恢复状态。
- 页面和文件写入使用 CAS；过期 writer 不能推进 current pointer。
- 冲突保留候选、原始 bytes、审阅状态和可释放备份，不直接覆盖人工文件。
- rename/delete/restore 推进 projection epoch，并让旧 epoch job 进入 superseded。

### 5.2 GBrain projection 与 citation

- 托管 Markdown 写入 `id` 和 `lgdo_page_id`。
- 批次创建时记录 page、mapping、job snapshot，完成时重新校验所有快照。
- 同 desired state 的多个 page job 可以共同成功；不同 desired state 直接 fail-closed。
- delete reconcile 只在可权威归因时暂时排除自身 page protection；NULL owner、其他 page 和同 DTO 碰撞仍保留。
- delete 成功只 resolve 自身 page protection；失败、restore before request 和 restore during request 保留保护并走 supersede/CAS。
- 任一 `finish_claimed` CAS 失败时，映射、generation、已完成 job 和保护写入在同一事务中回滚。
- citation 只接受经过 ACL 和来源存在性过滤的证据，GBrain 结果不能绕过本地授权。

### 5.3 Vault watcher 与 Obsidian

- watcher 首次 `anext` 前完成 ready 状态，避免漏掉首个事件。
- watcher restart、cancel、`aclose` 和 Future/awaitable 路径均有收口。
- VaultSyncService 使用单一 `vault-delete-expiry` task，首轮立即执行；stop 时设置 Event、cancel 并 await；异常写入 `last_error` 后继续。
- 自动 reconcile 与手工 reconcile 共用持久化 single-flight lease。
- 外部文件先做稳定性观察、大小上限和 frontmatter 解析，再写 revision。

### 5.4 安全与测试隔离

- `auth_dev_fallback_enabled` 默认 `False`，只有 `app_env=development` 且显式开启时允许匿名/可信开发 header。
- OIDC 关闭时不再接受未签名 Bearer；bootstrap 管理员密码没有 `admin` 默认值。
- upload domain 在写盘前验证，并证明 resolved path 位于 upload root 内。
- PostgreSQL 测试使用 UUID 数据库，创建前拒绝复用，创建后记录 ownership，finally 精确 terminate/drop/verify。
- pytest 默认网络门禁拒绝 `8000/8011/8787` 和外网；允许动态 loopback 与本地 PostgreSQL，并清理 DeepSeek/GBrain 外部凭据及子进程环境。

## 7. 残余风险与边界

1. **没有原生插件**：冲突列表、同步状态和 citation 预览仍位于 Web 控制台；若“Obsidian 实现”定义为原生侧边栏/命令面板，本项目还未满足。
2. **运行配置必须显式提供**：GBrain projection 需要专用 token、managed source、allowed root 和 source ID。代码默认 fail-closed，旧进程不会因 Git 合并自动获得新配置。
3. DeepSeek、GBrain HTTP MCP 和 PostgreSQL 是可选/外部依赖；没有凭据或服务异常时只能得到本地抽取式回答或失败保护状态。
4. 网络门禁是 pytest 测试安全边界，不是生产出站防火墙；生产环境仍应在网络层限制外连和管理端口。
5. 当前报告没有声称新的准确率提升；31 题基线为 GBrain OFF `16/31`、ON `14/31`，ON 的 P95 增加约 `948.63ms`。生产默认应保持关闭，直到目标数据集证明稳定收益。
6. 项目当前没有固定的 Python lint 依赖；建议在 CI 明确加入并锁定 ruff，而不是依赖开发机全局安装。

## 9. 建议验收标准

- 新建、编辑、rename、delete、restore 在 Vault、`wiki_pages`、revision、RAG 和 GBrain projection 中最终收敛，且每个页面保留可追溯 `page_id`。
- 任意 stale writer、旧 epoch job、保护 collision 或 CAS 失败都不会覆盖新状态或误删映射。
- citation 中每个来源均能回到授权的 source/page/revision，未授权来源不会进入 prompt。
- 关闭 DeepSeek/GBrain 时核心入库和本地回答仍可运行；服务恢复后 outbox/reconcile 可自动补偿。
- 真实动态端口 E2E 业务总时长小于 30 秒，固定 `8000/8011/8787` 不被测试触碰。
- CI 在无外网环境仍能完成默认测试；需要 PostgreSQL/GBrain 的测试明确使用动态、隔离资源。
- 交付提交可从 `main` 追溯，部署实例的 `/health` 与显式 `.env` 配置一致；其他开发分支和未提交工作不得在合并时被覆盖。
- 登录后控制台可见 Vault 状态、对账按钮和 Obsidian deep link；若产品要求原生插件，则另以插件安装、命令面板和侧边栏验收，不与当前文件工作流混淆。

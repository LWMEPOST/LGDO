**问题1：GBrain 本地 stdio 查询会在每次问答请求中启动一次外部进程**
- 位置：`app/search.py:57`、`app/gbrain.py:198`、`app/gbrain.py:199`、`app/gbrain.py:200`、`app/gbrain.py:310`
- 问题：`ask()` 在每次请求中都会调用 `query_gbrain()`；当未配置 HTTP endpoint 时，`query_gbrain()` 会通过 `LocalMcpClient` 启动 `bun run src/cli.ts serve`，完成 MCP 初始化后再查询。这个行为在 `GBRAIN_ENABLED=true` 时会进入每一次问答的关键路径。
- 风险：问答接口会被外部进程启动、MCP 初始化、GBrain 查询超时共同影响；默认查询超时为 45 秒，高并发或 GBrain 初始化变慢时容易出现明显延迟。
- 建议：优先改成常驻 HTTP MCP 服务，或在应用内做持久化/复用客户端；如果继续用本地 stdio，建议只在本地 RAG 低置信度或无命中时触发，或加短超时、熔断和缓存。

**问题2：编译知识库后同步全量导入 GBrain 会阻塞接口**
- 位置：`app/wiki.py:207`、`app/wiki.py:208`、`app/gbrain.py:136`、`app/gbrain.py:144`
- 问题：`gbrain_import_on_compile=true` 时，`compile_wiki()` 会同步执行 `import_vault_to_gbrain()`；导入命令固定扫描 `vault/wiki` 并带 `--fresh`，而不是只导入本次 domain/source_ids 影响的页面。
- 风险：编译接口可能被全量导入阻塞，默认导入超时为 600 秒；资料量变大后，用户会感觉“编译卡住”，并且小范围编译也可能触发不必要的全库刷新。
- 建议：将 GBrain 导入改为后台任务，或至少按本次编译的页面集合增量导入；生产默认建议保持 `GBRAIN_IMPORT_ON_COMPILE=false`，由显式导入动作触发。

**问题3：GBrain 查询失败会被静默降级，线上排障信息不足**
- 位置：`app/gbrain.py:198`、`app/gbrain.py:201`、`app/gbrain.py:211`、`app/gbrain.py:219`、`app/search.py:114`
- 问题：`query_gbrain()` 和 `_query_gbrain_with_caller()` 捕获 `GBrainError` 后直接返回空列表；`retrieval_strategy` 只暴露 `gbrain_enabled` 和 `gbrain_hits`，无法区分“禁用、不可用、超时、鉴权失败、工具报错、确实无结果”。
- 风险：用户看到的是普通低命中结果，运维侧难以判断是数据缺失还是 GBrain 调用失败，也不利于评估 GBrain 接入后的真实收益。
- 建议：保留非阻断降级策略，但把 `gbrain_status`、`gbrain_error` 或 `gbrain_note` 写入 `retrieval_strategy` 和 `gbrain_log.md`；对超时/鉴权错误做分类型记录。

**问题4：HTTP MCP 分支缺少真实请求形态测试**
- 位置：`app/gbrain.py:444`、`app/gbrain.py:473`、`tests/test_gbrain_integration.py:33`、`tests/test_gbrain_integration.py:60`
- 问题：现有 GBrain 测试主要 monkeypatch `call_gbrain_tool()`，验证了 fallback 逻辑和上下文拼接，但没有覆盖 `_call_http_mcp()` / `_post_mcp()` 的真实 HTTP 请求头、Bearer Token、SSE 解析、HTTP 错误和 JSON-RPC 错误路径。
- 风险：切换到 `GBRAIN_ENDPOINT` 后，HTTP 鉴权、响应解析或服务端错误格式变化可能在测试中无法提前暴露。
- 建议：增加一个本地 fake HTTP MCP server 或 monkeypatch `urllib.request.urlopen` 的测试，至少覆盖 initialize、tools/call、401/500、text/event-stream 四类响应。
